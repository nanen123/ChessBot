# 010. 0-B 집중 복습

0-C(유리한 교환)를 배우는 동안 0-B(안전한 포획)의 성능이 떨어지는 경우를 보완한다. 관측·행동·보상은 바꾸지 않고, 학습에 공급하는 난이도의 비중을 조절한다.

## 학습 비중

| 모드 | 0-A | 0-B | 0-C |
|---|---:|---:|---:|
| 일반 0-C 학습, 기본 복습률 20% | 10% | 10% | 80% |
| 0-B 집중 복습 | 10% | 50% | 40% |

집중 복습은 0단계 난이도 2에서만 적용한다. 일반 모드에서는 기존 Inspector의 Capture Review Probability를 따른다. 복습 모드는 기존 복습률에 추가하는 것이 아니라 해당 비중으로 대체한다. 기물별 균형 추출과 새로운 포획 배치 생성은 그대로 적용된다.

## 자동 진입·회복

- 0-C 평가에서 0-B의 기존 평가 또는 추가 검증이 유지 기준 75% 미만이면 집중 복습을 켠다.
- 두 점수가 모두 80% 이상인 평가가 연속 2회 나오면 집중 복습을 해제한다. 중간에 어느 하나라도 80% 미만이면 회복 횟수를 0으로 초기화한다.
- 회복 전에는 다음 커리큘럼으로 승급하지 않는다. 기존 유지/승급 기준, 최소 학습 스텝, 연속 통과 조건도 계속 검사한다.
- 회복과 기존 승급 조건을 같은 평가에서 모두 충족하면 바로 다음 단계로 넘어갈 수 있다. 80% 회복 조건을 통과해도 0-A나 0-C 등 다른 조건이 미충족이면 일반 비중으로 0-C 학습을 계속한다.
- 일반 비중으로 돌아간 뒤 0-B가 다시 75% 미만이면 집중 복습을 재개한다. 75%~80% 구간은 직전 모드를 유지해 잦은 전환을 피한다.
- 자동 복습은 이후 단계 1~5에 적용하지 않는다. 이 단계에서 과거 0-B가 약해져도 기존 유지 검사는 계속 승급을 막는다.

모드가 바뀌면 기존의 환경 리셋 경로를 통해 반영하고, 이전 비중의 replay buffer를 비워 새 비중의 경험을 채운다. 모델 가중치는 유지한다. 복습 여부와 회복 횟수는 `success_curriculum.json`에 저장하므로 같은 설정으로 `--resume`하면 이어진다.

## 현재 모델 보완 실행

현재 학습은 자동 중단하지 않았다. 정상 종료해 저장한 다음 Unity의 `ChessBot > Training > Build Windows Training Player`로 재빌드한다. 새 환경은 Python에서 전달한 복습 비중을 읽어야 하므로 이번 변경에는 재빌드가 필요하다.

```powershell
python Tools/TrainChessSuccess.py config/chess_sac.yaml --run-id=curriculum_6_repair --initialize-from=curriculum_6 --repair-capture-b --env=output/chess-training/ChessTraining.exe --no-graphics --time-scale=30 --num-envs=12 --torch-device=cuda
```

`--repair-capture-b`는 새 run을 0-C + 집중 복습 상태로 시작한다. 따라서 0-A부터 승급을 다시 기다릴 필요가 없다. 원본 run의 커리큘럼 상태에서 0-C까지 도달했는지 검사한다. 원본 모델과 기록은 수정하지 않는다. 기존 모델 가중치를 가져오고 replay buffer, 스텝, 승급 및 회복 연속 횟수는 새로 시작한다. 더 뒤의 단계까지 간 모델도 이 옵션을 명시하면 0-C 복습부터 시작한다.

이 새 실행을 중단했다가 이어갈 때는 초기화 옵션 둘을 빼고 `--resume`을 사용한다.

```powershell
python Tools/TrainChessSuccess.py config/chess_sac.yaml --run-id=curriculum_6_repair --resume --env=output/chess-training/ChessTraining.exe --no-graphics --time-scale=30 --num-envs=12 --torch-device=cuda
```

`--repair-capture-b` 없이 새 학습을 시작하면 기존처럼 0-A에서 시작하고, 나중에 0-C의 0-B 유지 점수가 떨어질 때 자동 복습이 작동한다. 설정 fingerprint가 바뀌었으므로 변경 전 run에 직접 `--resume`하지 않는다. `mlagents-learn`만으로는 자동 회복 판단과 승급을 실행하지 않으므로 위 어댑터를 사용한다.

## 조절 위치

`config/chess_evaluation.yaml`:

```yaml
capture_b_repair:
  enabled: true
  recovery_threshold: 0.80
  recovery_passes: 2
```

진입 기준은 기존 `capture_retention_thresholds[1]`인 0.75다.

`config/chess_sac.yaml`의 환경 파라미터:

```yaml
capture_repair_active: 0
capture_repair_a_probability: 0.10
capture_repair_b_probability: 0.50
```

활성 여부는 어댑터가 덮어쓴다. 0-C 확률은 `1 - A - B`이며, A/B는 음수가 아니고 합계가 1 이하여야 한다. 기본 비중에서는 C에도 40%를 남겨 기존 학습을 계속한다.

## 확인할 지표

- `Evaluation/CaptureRepair/Active`: 평가 후 집중 복습 상태, 0 또는 1.
- `Evaluation/CaptureRepair/RecoveryPasses`: 연속 80% 회복 횟수.
- `Curriculum/CaptureRepairActive`: 실제 Unity 환경의 복습 상태.
- `Curriculum/CaptureSampling/0`, `/1`, `/2`: 실제 에피소드 난이도별 배정 비율. 단기간에는 확률 때문에 표의 비율과 다를 수 있다.
- `Evaluation/Capture1/Success`, `IndependentSuccess`: 회복을 판단하는 0-B의 두 검증 점수.
- `Evaluation/Capture1/Strata/<기물>/Success`, `IndependentSuccess`: 0-B의 기물 종류별 검증 결과. 작은 표본의 기물 점수 하나만으로 자동 가중치를 바꾸지는 않는다. 학습 배치는 기존의 기물 균형 추출을 유지한다.

기능 연결과 회복 조건은 테스트할 수 있지만 실제 기력 회복은 재학습으로 확인해야 한다. 생성 배치 성공률이나 TrainingSuccess만으로 복습을 해제하지 않는다.

## 한 수 문제의 리셋 보완

검증 중 ML-Agents의 `NotifyAgentDone`이 이미 종료 처리된 비행동 상대의 다음 종료 알림을 생략하는 경로를 확인했다. `OnEpisodeBegin`에서 `SetReward(0)`을 호출해 해당 상대에게 쌓인 이전 보상이 다음 에피소드에 남지 않도록 했다. 한 수 문제는 양쪽의 `CompletedEpisodes`가 같지 않을 수 있으므로, 공동 리셋 테스트는 실제 `OnEpisodeBegin` 호출 횟수로 검증한다. 이 현상이 0-B 성능 저하의 원인이라고 단정하지 않는다.

## 검증 결과

- Python 승급·복습 회귀 검사 30개 통과: 자동 진입, 75~80% 유지 구간, 두 검증·연속 회복, 재진입, 상태 재개, 복습 중 승급 차단.
- Unity EditMode 98개 및 최종 PlayMode 26개 통과. 난이도 배정 비율과 비행동 상대 보상 초기화 포함.
- 런타임/에디터 컴파일 및 핵심 체스 규칙 47개 통과. Windows 검증용 빌드 성공.
- 별도 CUDA 실행 `repair-check-20261002`가 기존 모델 복사본에서 0-C 집중 복습으로 시작해 413 step 후 정상 종료했다. 초기 두 통계 구간의 0-B 비중은 각각 50.0%, 53.6%였다. 평가 회복 횟수 1→2 및 복습 해제 후 승급, 저장 상태 재로딩을 확인했다.
- CUDA 검사는 검증 전용 설정의 회복/승급 점수 기준을 0으로 낮춘 기능 연결 검사다. 운영 YAML의 회복 기준 80%, 연속 2회와 기존 승급 기준은 유지했다. 짧은 검사 결과로 실제 기력 회복을 주장하지 않는다.

산출물은 `output/training-validation/repair-editmode.xml`, `repair-final-playmode.xml`, `repair-compile.log`, `repair-build.log`, `repair-smoke-verification.json`에 있다. 기존 학습 run과 사용자용 실행 파일은 수정하지 않았다.
